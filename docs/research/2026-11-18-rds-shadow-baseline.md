# Research Brief — RDS shadow client baseline

- Date: 2026-11-18
- Question: Как устроен публичный PowerShell-скрипт shadow-подключения и какой безопасный Rust-клиент из него следует, если допуск остаётся у Windows, а не у программы.
- Scope / out of scope: разбор `rds_shadow_connect` и варианты v1. Не ТЗ, не реализация, не настройка GPO на ферме.

Источник скрипта: <https://github.com/RinHell/pshell_sript_connect_user_rds/blob/main/rds_shadow_connect> (raw, один файл, один коммит, README нет).

## Findings

- Скрипт — WinForms-панель на ПК специалиста. Опрашивает зашитый список хостов, показывает сеансы, запускает `mstsc.exe /v:<host> /shadow:<id> /control`, умеет `logoff`. — raw script — high
- Онлайн-проверка — TCP 3389, таймаут 500 мс. Это не проверка прав и не проверка службы сеансов. — raw script — high
- Список сеансов — разбор текста `query session` и `quser`. Уже есть ветка под русскую локаль (`Active|Актив`). Формат вывода хрупкий. — raw script — high
- Права читаются через CIM `root\CIMV2\TerminalServices`, класс `Win32_TSPermissionsSetting`, listener `RDP-Tcp`, DACL текущего пользователя и его групп. Биты в скрипте: 16 shadow, 32 «отключение», 64 logoff, 128 message. — raw script — high
- Бит 32 в скрипте подписан как Disconnect. У WINSTATION disconnect обычно `0x200`, не `0x20`. Shadow `0x10` и logoff `0x40` выглядят обычно. Перед копированием биты сверить на стенде. — сопоставление со стандартной раскладкой WINSTATION — medium
- При ошибке WMI скрипт включает Shadow и Logoff (`CanShadow = $true`, `CanLogoff = $true`). Это fail-open для кнопок. Сам `mstsc` при этом права не повышает. — raw script — high
- Флага обхода согласия нет. Согласие всё равно решает политика Session Host, не скрипт. — raw script — high
- Всегда передаётся `/control`. Режима «только просмотр» нет. — raw script — high
- Аудита нет: ни кто подключился, ни к кому, ни зачем. Сообщения в сеанс нет, хотя бит message читается. — raw script — high
- Картинка shadow открывается только в интерактивном сеансе того, чья учётка имеет право Remote Control. Вынести просмотр на службу или Linux-клиент без своего RDP-стека нельзя. — модель Windows shadow — high
- Обход клиента: если право Remote Control уже есть, специалист может вызвать `mstsc /shadow` сам. Программа не является границей допуска. — модель Windows shadow — high
- GPO remote control — политика компьютера на Session Host. Она задаёт потолок (view или full control) и требование согласия для всех, а не для одной AD-группы. Разделение view/control по группам политика само не делает. — модель Windows shadow — high
- Secure desktop (UAC) через shadow обычно не виден и не управляется. Это ограничение ОС. — эксплуатационная модель RDS — medium

## User decisions (2026-11-18)

- Клиент v1: Windows-ПК специалиста.
- Допуск: группа AD + GPO. Не JIT и не «просто переписать скрипт».
- По умолчанию просмотр; управление — отдельное действие.
- Согласие сотрудника обязательно. Обход согласия в продукт не входит.
- Действия v1: список сеансов и статусов, shadow, сообщение в сеанс, logoff.
- Аудит: Windows Event Log + локальный файл + файл на сетевой шаре + syslog. Нужен просмотрщик с фильтрами для разбора инцидентов. Содержимое экрана не логировать.
- Заявка обязательна перед shadow, сообщением и logoff. В v1 ITSM не опрашиваем.
- Три группы AD. Отдельное право ОС есть у message и logoff. View и control — один бит Remote Control; разница view/control в клиенте не является границей ОС.
- Обход `mstsc /control` в v1 не закрываем: ТП 5–8 человек, им доверяют. Усложнение — следующие версии.
- Текст сообщения в журнале полный. UI — русский и английский.
- 2026-11-18, уточнение: syslog и блокировка действия сняты с v1. Журнал — только JSONL (локально и, если задано, шара). Syslog или сервер сбора — позже, тем же JSON. Скриншот в syslog не кладём: протокол для этого не годится.
- Ферма: Server 2016–2025, один домен, брокер, порт 3389. Имена групп и узлов только в INI. Тестового узла нет.

## Options

1. **Клиент + политика ОС (рекомендуется).** Rust GUI на Windows. Список сеансов через WTS API, не через разбор текста. `mstsc` без флага обхода согласия; `/control` только по отдельной кнопке. Кнопки fail-closed. Четыре приёмника аудита с одной JSON-схемой. Просмотрщик читает копию на сервере логов, не файл, который пишет клиент.
2. **JIT-группа на время заявки.** Сильнее против обхода `mstsc`, но нужен привилегированный сервис. Не v1.
3. **Свой RDP/shadow-стек или Linux-клиент.** Не v1.
4. **Только перенос скрипта на Rust.** Не принимает решения по безопасности.

## Fit for this project

- applicable — вариант 1. Проект пустой (шаблон), целевая ОС клиента — Windows, разработка сейчас на Linux. Проверка WTS/GPO возможна только на Windows-стенде.
- partial — просмотрщик syslog в том же репозитории вторым бинарём. Имеет смысл, если нет готового Graylog/Loki/Wazuh.
- no — брокер, который «подключается вместо специалиста». Shadow не проксируется чужой учёткой в чужой рабочий стол без своего протокола.

## Risks

- Logoff необратим для несохранённой работы. В v1 только с отдельным правом, номером заявки и подтверждением.
- Клиентский файл и шара подделываемы тем, кто имеет право записи. Для инцидента источник — приёмник syslog, которым специалист не управляет.
- Полный список пользователей в syslog на каждый Refresh — лишние ПДн. В аудит писать действия, не каждый опрос.
- Текст сообщения сотруднику может содержать ПДн. По умолчанию логировать длину и хеш, не текст — нужно подтверждение.
- Имена хостов из публичного скрипта не копировать в репозиторий, пока не подтверждено, что это желаемый инвентарь.

## Gaps

- Версия Windows Server и ПК специалистов, домен, состав фермы, порт RDP, есть ли Connection Broker.
- Есть ли тестовый Session Host.
- Имена AD-групп и кто применяет GPO.
- Где работает приёмник журнала, срок хранения, кто открывает просмотрщик.
- Версии узлов и ПК, имена групп, тестовый стенд.
