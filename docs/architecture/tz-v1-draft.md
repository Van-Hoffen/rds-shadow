# ТЗ v1 — RDS Shadow (черновик)

- Статус: **не утверждено**
- Дата: 2026-11-18
- Опора: `docs/research/2026-11-18-rds-shadow-baseline.md`
- Кода ещё нет. Это спецификация для согласования, не описание готовой программы.

## 1. Зачем

Специалист техподдержки со своего Windows-ПК видит сеансы сотрудников на ферме RDS, подключается теневым просмотром или управлением, может отправить сообщение и завершить сеанс. Факт действия пишется в файлы журнала.

Программа не выдаёт права. Разрешение или отказ делает Windows.

## 2. Не цель v1

- Обход согласия, флаг `/noConsentPrompt` и любой эквивалент.
- Свой RDP-стек и теневое подключение с Linux. `mstsc /shadow` открывает картинку только в интерактивном сеансе Windows.
- Syslog, свой приёмник, сервер сбора логов, блокировка действия из-за недоступного центрального журнала.
- Скриншоты сеанса. Обычный syslog их не перевозит: кадр экрана — это сотни килобайт, а не строка события; один кадр в секунду — поток на гигабайты в день. Когда появится сервер сбора, кадры кладут в отдельное хранилище, в журнал — только ссылка. Не в v1.
- JIT, проверка заявки в ITSM, disconnect, хранение паролей, зашитые имена узлов и групп.
- Настройка прав `RDP-Tcp` из клиента (редактор WMI). Вынесено в `archive/rdp-tcp-permissions/`; программа прав не выдаёт (см. §1).

## 3. Термины

| Термин | Значение здесь |
|--------|----------------|
| Специалист | личная доменная учётка ТП. Для shadow — интерактивный вход на Windows 10/11 |
| Сотрудник | владелец целевого сеанса на узле RDS |
| Узел сеансов | Windows Server 2016, 2019, 2022 или 2025 с сеансом RDS |
| Брокер | RD Connection Broker этого единственного домена. Порт RDP — 3389 |
| Сеанс | сессия на конкретном узле, числовой ID |
| Просмотр | `mstsc /v /shadow` без `/control` |
| Управление | тот же вызов с `/control` |
| Согласие | запрос ОС у сотрудника. Решает политика узла |
| Remote Control | одно право ACL `RDP-Tcp`. Не делится на «смотреть» и «управлять» |
| Заявка | обязательная непустая строка. ITSM в v1 не опрашиваем |
| Журнал v1 | JSONL-файлы. Не syslog |

Список Linux (Debian, Alt, Fedora, Red Hat, RedOS, Astra) и Windows 10/11 в ответе про клиентов — это ОС, с которых сотрудники ходят на ферму. Теневой клиент v1 с этих Linux не запускается. Если специалист сидит только на Astra или RedOS и своего Windows-сеанса нет, v1 ему shadow не даст.

## 4. Ферма

- Один домен. Брокер есть. Порт 3389.
- Тестового узла нет. Первая проверка — на продуктовой ферме.
- Проверка на продукте не повод пробовать logoff и управление на чужом сеансе. Первый проход: список и просмотр с согласия добровольца. Logoff и управление — только на сеансе, владелец которого ждёт этого. Logoff уничтожает несохранённую работу.

## 5. Образец и что не переносим

Образец: <https://github.com/RinHell/pshell_sript_connect_user_rds/blob/main/rds_shadow_connect>

Переносим смысл: таблица сеансов, поиск, shadow через `mstsc`, сообщение, logoff с подтверждением.

Не переносим: fail-open при ошибке WMI, всегда `/control`, разбор текста `query session` / `quser`, зашитый список узлов, отсутствие журнала.

Кнопки включаются по группам из конфигурации, сверенным с токеном текущего входа. Отказ по факту делает ОС. Имена групп в код не компилируются.

## 6. Состав v1

| Программа | Где работает | Задача |
|-----------|--------------|--------|
| `rds-shadow` | Windows 10/11 специалиста | список, просмотр, управление, сообщение, logoff, запись JSONL |
| `rds-shadow-audit` | Windows и Linux | чтение каталога JSONL, фильтры, экспорт CSV |

Отдельного приёмника в v1 нет. Картинку shadow приёмник не видит: её нет.

Встроенного запрета в просмотрщике нет. Кто может читать каталог журнала, тот открывает события. Защита каталога — права папки, не логин в программе. Папка, где лежит exe, границей не является: программу можно скопировать.

## 7. Конфигурация

Файл INI, не реестр и не исходник. Секретов в нём нет: паролей программа не спрашивает и не хранит. Вход — текущий доменный токен Windows-сеанса.

Рядом с программой лежит пример без боевых имён: `rds-shadow.example.ini`. Рабочий файл администратор кладёт сам, в git его не коммитят.

```ini
[connection]
mode = broker
broker = broker.example.domain
rdp_port = 3389

[servers]
list =

[groups]
view =
control =
logoff =

[audit]
log_dir = C:\ProgramData\rds-shadow\logs
share_dir =

[ui]
language = auto
```

- `mode = broker` — спросить брокера от имени текущего входа, показать коллекции, узлы и пользователей, фильтровать в UI.
- `mode = servers` — не ходить на брокера, опросить узлы из `list`.
- Оба значения доступны в настройках. Если брокер указан и список тоже, режим выбирает специалист, по умолчанию берётся `mode`.
- Имена групп пустые в примере. Пока ключ пуст, соответствующая кнопка скрыта, а не включена.
- `share_dir` необязателен. Это каталог на шаре для разбора, пока нет сервера сбора.

Как именно брокер отдаёт коллекции (RDMS CIM или другой API роли), выбирается при реализации после одного чтения на ферме. В код не зашивается имя боевого брокера. На ПК специалиста не требуем RSAT, если опрос брокера текущим токеном возможен без него. Если ферма пускает к списку только через модуль, которого на ПК нет, это блокер реализации, его не обходят сохранённым паролем.

Shadow всё равно идёт на узел сеанса и ID сеанса. Брокер нужен, чтобы не вести список узлов руками.

## 8. Поведение клиента

Список — API WTS, не текст `query`. Поля: коллекция (если пришла от брокера), узел, пользователь, ID, состояние, время входа и простой — если API их отдаёт. Иначе поле пустое. Сам опрос в журнал не пишется.

Перед просмотром, управлением, сообщением и logoff заявка обязательна.

| Действие | Условие в клиенте | Вызов | Подтверждение |
|----------|-------------------|-------|----------------|
| Просмотр | группа View, сеанс Active | `mstsc /v /shadow` | заявка |
| Управление | группа Control, сеанс Active | плюс `/control` | заявка и отдельный вопрос |
| Сообщение | группа View | `WTSSendMessage` | заявка, текст виден до отправки |
| Logoff | группа Logoff | `WTSLogoffSession` или `logoff` | заявка, показ пользователя и узла, ввод имени без домена (отсекается по `\`) |

Logoff выполняется в два шага: после подтверждения окно закрывается, клиент опрашивает список сеансов выбранного узла (интервал 2 с, максимум 40 с), ждёт исчезновения пользователя с этим ID и показывает уведомление «Логофф выполнен» внизу справа; фокус окна не переходит. Опрос в журнал не пишется. Если за 40 с сеанс всё ещё виден — предупреждение, а не успех.

### Отображение теневого сеанса (несколько мониторов)

- Режим по умолчанию — **«Детали 1:1»**: нативная картинка с прокруткой к нужному монитору. «Обзор» — весь стол вписан. Переключение — **на лету** в подвале окна рендерера. `mstsc` для захвата запускается с `smart sizing:i:0` (нативный кадр); смена разрешения сеанса требует переподключения.
- Окно сеанса открывается на том же мониторе, где открыт `rds-shadow`.
- Способ отображения — **свой рендерер**: кадр окна `mstsc` захватывается через `Windows.Graphics.Capture` и рисуется в нашем окне с zoom/pan/crop по мониторам. Риски и поэтапный план — решение 0005.
- Компоновка окна рендерера: сеанс — в **заголовке**; режим и масштаб — в **подвале** одной строкой; выбор монитора кнопками не делается. **Мини-карта** включается кнопкой или `Ctrl+M` и показывается при масштабировании. Подсказки: при подключении плашка на 5 с, затем кнопка «?»; нажатие разворачивает панель возможностей окна (функции с кратким описанием), повторное — сворачивает.
- Дополнительно: **мини-карта** (кнопка/`Ctrl+M`, показывается при масштабировании), запоминание режима и положения окна на узел. Горячие клавиши основных функций окна (мини-карта, режим, масштаб, панорамирование) настраиваются в разделе **«Горячие клавиши»** настроек.
- Ограничения: жёлтая рамка захвата, латентность; проброс ввода для управления — отдельная задача.

Ни один вызов не получает флаг обхода согласия. Нет группы в токене — кнопки нет. ОС отказала — показать отказ и дописать `denied` или `fail` в файл, если файл пишется.

Недоступный шаровой каталог, отсутствие syslog и будущий сервер сбора действие не отменяют.

Старт shadow пишется до запуска `mstsc`. Окончание — когда завершился запущенный нами процесс.

## 9. Политика узлов

На узлах: полное управление с разрешением пользователя. Включает это администратор фермы, не установщик.

Общая учётка ТП не используется.

Остаточный риск v1 принят. Член View может сам запустить `mstsc /shadow /control`, если политика узла разрешает полное управление. ТП — 5–8 человек, им доверяют. Закрытие обхода — не v1.

## 10. Журнал

Только файлы. Syslog в v1 не отправляем и не ждём.

| Куда | Когда |
|------|--------|
| `log_dir\<компьютер не нужен, это локальный ПК>\YYYY-MM-DD.jsonl` | каждая попытка действия |
| `share_dir\<имя ПК>\YYYY-MM-DD.jsonl` | если `share_dir` задан и шара доступна |

Файл на шаре — отдельный на ПК и на день, чтобы две одновременные записи не перемешали строки. Просмотрщик читает дерево каталогов, не один общий файл.

Ошибка записи на шару или пустой `share_dir`: предупреждение в интерфейсе, действие выполняется, локальный файл всё равно пытаемся дописать. Ошибка локальной записи тоже не отменяет уже подтверждённое действие; в интерфейсе остаётся явная ошибка записи. Это ослабление относительно прежнего «нет OK — нет действия». Принято: сначала не мешать работе ТП, сервер сбора — следующая версия.

В файл не попадает картинка, заголовок окна, буфер и пароль. Текст сообщения пишется целиком: так решено, ТП не должна писать туда закрытые данные, программа текст не маскирует. Полный список сеансов на каждый Refresh не пишется.

События: `shadow.start`, `shadow.end`, `shadow.denied`, `message.send`, `message.denied`, `logoff.requested`, `logoff.ok`, `logoff.fail`, `logoff.denied`.

Одна строка JSON, UTF-8:

```json
{"v":1,"ts":"2026-11-18T09:12:33.123Z","event":"shadow.start","result":"ok","specialist":"CORP\\a.ivanov","specialist_sid":"S-1-5-21-example","workstation":"WS-042","target_user":"CORP\\m.petrov","target_server":"ts03","session_id":14,"session_state":"Active","mode":"view","ticket":"SD-12345","client_version":"0.1.0","message_text":null,"message_len":0,"duration_ms":null,"error":null}
```

`ts` — UTC. `mode` — `view`, `control` или `none`. `duration_ms` — в `shadow.end`. `message_text` — в `message.send`.

Формат строки тот же, каким позже можно кормить syslog или сервер сбора. В v1 транспорт — только файл.

## 11. Просмотрщик

Windows и Linux. Открывает выбранный каталог JSONL. Фильтры: время, специалист, сотрудник, узел, событие, заявка, результат. Экспорт CSV. Править и удалять события нельзя.

Язык клиента и просмотрщика: русский и английский. По умолчанию язык ОС, если он ru или en, иначе английский. Переключение из меню.

## 12. Ограничения

- Согласие нельзя включить из программы, если политика узла уже разрешает вход без спроса.
- UAC secure desktop через shadow обычно не виден и не нажимается.
- К отключённому сеансу shadow не подключается.
- Обход кнопки управления прямым `mstsc /control` в v1 принят.
- Журнал v1 легко не донести до разбора: локальный файл можно удалить, шара может быть пустой. Это цена решения не блокировать работу.

## 13. Приёмка v1

1. Имена узлов, брокера и групп не зашиты в код. Пустая группа — скрытая кнопка, не включённая.
2. Режим брокера и режим списка оба выбираются из настроек. Пароль нигде не сохраняется.
3. Специалист без группы View не запускает shadow из клиента.
4. Просмотр не передаёт `/control` и не передаёт обход согласия.
5. Управление в клиенте недоступно без группы Control.
6. Logoff недоступен без группы Logoff и без ввода имени сотрудника.
7. Пустая заявка блокирует все четыре действия.
8. Недоступная шара и отсутствие syslog не блокируют действие. Локальный JSONL содержит попытку, если диск позволил записать.
9. Просмотрщик на Windows и на Linux находит событие по заявке и сотруднику. В журнале нет кадра экрана.
10. Первая проверка на продуктовой ферме — список и просмотр с согласия добровольца. Не logoff чужого сеанса.

Пункты 2–7 и 10 на Linux-машине разработки не доказываются.

## 14. Уже решено

- Узлы: Windows Server 2016–2025. Один домен, брокер, порт 3389.
- Теневой клиент: Windows 10/11, текущий доменный вход.
- Просмотр по умолчанию, управление отдельно, согласие обязательно.
- Заявка обязательна. Три группы, имена только в INI.
- Журнал v1 — файлы. Действие не зависит от syslog. Syslog или сервер сбора — следующая версия, формат строки уже совместим.
- Текст сообщения в журнале полный. Скриншотов нет.
- UI ru и en. Просмотрщик без своей авторизации.
- Обход `mstsc /control` в v1 не закрываем.

## 15. Открыто

- Подтвердить, что специалист всегда имеет Windows-сеанс. Если нет — v1 не закрывает эту смену.
- Кто на ферме ставит политику согласия.
- Срок хранения файлов на шаре. Программа в v1 сама не чистит журнал.
