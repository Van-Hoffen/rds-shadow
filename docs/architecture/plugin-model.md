# Модель плагинов RDS Shadow

- Статус: предложено 2026-11-19 (проект, реализация не начата)
- Источник подхода: модель плагинов `fgbm/depesha` (`plugins/README.md`, `src/plugin-api/`). Анализ — `docs/research/2026-11-19-llm-checkable-ui-and-plugins.md`.
- Тип: explanation

## Философия

Ядро RDS Shadow делает ровно то, ради чего продукт существует: **список сеансов, shadow-подключение, сообщение в сеанс, logoff, журнал**. Всё остальное — плагин.

Что это значит в работе:

- новая возможность начинается с вопроса: **это список/подключение/сообщение/logoff/журнал?** Если нет — это плагин, и работа в том, чтобы найти или добавить нужную точку расширения, а не растить ядро;
- когда плагину нужно то, чего ядро не отдаёт, расширяется контракт (точка расширения) минимально — ровно настолько, насколько нужно плагину; поведение ядра без загруженного плагина не меняется;
- плагин-вкусовщина поставляется выключенным (`defaultOff`); плагин, который останавливает реальную ошибку, может поставляться включённым — различие по вреду, а не по предпочтению;
- вынести в плагин — не способ увильнуть от работы: если возможность стоит делать, плагин делает её полноценно, включая свою точку расширения в ядре.

## Что может быть плагином

Кандидаты на точки расширения (список черновой, до стабилизации контракта):

| Точка | Что даёт |
|---|---|
| действие на сеанс | своё действие в списке/детали сеанса (помимо message/logoff) |
| проверка согласия / preflight | проверка перед shadow/управлением/logoff (политика, заявка) |
| фильтр аудита | свой фильтр/разрез журнала в просмотрщике |
| экспортёр/формат аудита | свой формат выгрузки (CSV, отчёт, интеграция) |
| уведомление/хук | реакция на события (сеанс завершён, logoff выполнен) |
| секция настроек | своя группа настроек |

Точный набор точек фиксируется при проектировании контракта, не здесь.

## Контракт

- Единственный импортируемый контракт — модуль `plugin-api` (тип/trait). Всё, что плагин использует, идёт через него; прямой доступ к внутренностям ядра запрещён.
- Контракт защищён снимком (по аналогии с `plugin-api.snapshot.d.ts`): CI падает, когда публичная поверхность меняется без обновления снимка. Осознанное изменение — обновить снимок и отметить в changelog.
- Всё идёт через объект контекста: регистрация точек расширения (`ui.*`), вызовы сервисов ядра (`backend`), свои настройки (`settings` на id плагина), свои строки локализации.
- Точки расширения добавляются минимально; ядро без плагинов ведёт себя как прежде.

## Два вида плагинов

| | Built-in | Community |
|---|---|---|
| Где | в репозитории, собираются с ядром | устанавливаются отдельно |
| Язык | Rust, доверенный код | изолированная песочница (WASM) с правами |
| Видит | весь `plugin-api` | только то, что разрешено правами |
| Может | любые точки расширения | ограниченный набор точек + права |

Community-плагины — цель на будущее; в v1 реализуется только built-in-контракт и его точки. WASM-песочница проектируется позже, по аналогии с `ext://` Web Worker в depesha.

## Права и согласие

- Плагин декларирует права в манифесте, пользователь видит их **словами** до установки/включения, согласие записывается.
- Кандидаты прав (по аналогии): `sessions.read` (список/статусы), `sessions.control` (управление), `audit.read`, `network:<host>` (только публичный хост по имени, с валидацией против reserved-зон и форм IP).
- Опасные права (управление сеансом, `network`) — отдельное предупреждение.

## Что НЕ переносится

- TS/Svelte-компоненты, Web Worker `ext://`, Tauri IPC, `ctx.t` с `{en,ru}`-словарями — это специфика web-стека depesha. В RDS Shadow аналог контракта — Rust-trait/тип и штатная i18n проекта.
- WebDriver/Svelte e2e — нативный egui-клиент проверяется иначе (см. `docs/architecture/ui-standard.md`, `egui_kittest` как отдельная задача).
