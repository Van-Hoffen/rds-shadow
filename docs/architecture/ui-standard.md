# Стандарт написания интерфейса RDS Shadow

- Статус: принято 2026-11-19
- Источник подхода: `fgbm/depesha` (`design/mockups/`, `scripts/frontend-invariants.sh`, `scripts/mockup-kit.mjs`). Анализ — `docs/research/2026-11-19-llm-checkable-ui-and-plugins.md`.
- Тип: explanation

## Принцип

Интерфейс задаётся **машиночитаемым артефактом**, а не «на глаз». Агент LLM должен мочь проверить вид и структуру без человека: по разметке HTML, по контрактным атрибутам и по детерминированным скриншотам.

## Правила макета

1. Макеты лежат в `gui_html/rds-shadow/`, имя — `NN-имя.html` (порядковый номер + имя экрана); новая версия макета — отдельный файл `NN-имя-v2.html` (см. «Версии макетов»). Каждый макет — **самодостаточный одиночный файл**: без сети и внешних ссылок, открывается через `file://`.
2. Макет рисуется **до реализации**, один раз. Правки вида сверх нарисованного не делаются без перерисовки картинки — оператор соглашается на то, что видит.
3. Варианты стоят рядом, у каждого подпись; у вопросов — номера. Крупную развилку не решать самому — это вопрос оператору с картинкой. Мелкие нерешённые детали вида при реализации — по своей рекомендации, с перечислением в отчёте.
4. Термины и названия действий — из глоссария проекта; новые термины фиксируются в `docs/` до макета.

## Контракт разметки (машиночитаемый)

Каждый вопрос/вариант в макете размечается атрибутами, чтобы и панель «Ответы», и агент могли их прочитать:

- `data-q="1.1"` — блок вопроса или экрана;
- `data-q-title="…"` — название вопроса;
- `data-variants="А,Б,В"` — какие варианты есть (если на экране нарисованы не все);
- `data-recommended="Б"` — рекомендация автора;
- `data-variant="А"` вместе с `data-q` — блок варианта;
- `data-q-closed` — вопрос снят.

Интерактивность и доступность размечаются штатными `aria-*` и литеральными `role=`; элементы, которые проверяются e2e/скриптами, получают стабильные `data-*`-виды. Номера вопросов после публикации не меняются; буквы вариантов — кириллицей, как в тексте макета.

## Инварианты (baseline-гард)

Снимок контракта хранится как baseline и проверяется на регрессии:

- набор имён `aria-*`, литеральных значений `role=`, видов `data-*` (только тех, что читаются проверками);
- проверка падает **только на ухудшении** (пропавший aria/role/data);
- рост — строкой с причиной в файле исключений; «просто пересохранить baseline» недопустимо.

Для v1 baseline ведётся вручную/скриптом по HTML-макетам; перенос в CI — после утверждения pipeline. Нативный egui-GUI получает тот же контракт через `egui_kittest` + `accesskit` (дерево доступности) — отдельная задача, в этот стандарт пока не входит.

## Детерминированные скриншоты

Скриншоты для README/docs снимаются скриптом, а не вручную: фиксированные демо-данные (адреса `example.com`, фикс. даты), повторяемый прогон, результат в `docs/screenshots/`. Для HTML-макетов это открытие макета и снимок; для нативного GUI — после появления харнесса.

## Версии макетов и выбор вариантов

- **Макет не перезаписывается.** Новая версия — отдельный файл `NN-имя-v2.html` (потом `-v3`, …). Старые версии остаются, чтобы можно было вернуться к предыдущему представлению.
- Если у макета есть варианты, к которым нужен выбор: у каждого — контроль. `radio`, если выбрать можно **только один**; `checkbox`, если можно **несколько**. Контролы стоят рядом с вариантом или сразу под ним.
- В конце страницы — поле, которое **автоматически** заполняется заготовленным текстовым промтом по сделанным выборам, с кнопкой «Скопировать». Промт можно сразу передать агенту.
- Контролы вариантов привязываются к визуализациям: имя группы (`name`) — одна развилка, `data-label` — как выбор звучит в промте, `data-prompt` — у чекбоксов.
- **У каждого вопроса — короткий контекст** (абзац `.qctx` под заголовком): что именно спрашивается, что это **не** значит, и последствия/ограничения выбора. Без контекста вопрос непонятен человеку. Пример: «это про ваши локальные мониторы, а не про мониторы сотрудника; `/span` — только одинаковые горизонтальные».
- **Пояснения не живут внутри нарисованного окна.** В окне — только реальный UI (то, что видит и использует специалист во время сеанса). Почему/ограничения (DPI, латентность, проброс ввода, выбор архитектуры) выносятся отдельным блоком под макетом, визуально отделённым и помеченным «не часть окна». Иначе пояснительная проза мешает поддержке.

## Чек-лист приёмки вида

Перед тем как считать экран готовым, проверяются (по мотивам «как оператор оценивает интерфейс» в depesha):

- действие доводится с клавиатуры до конца — если после клавиши нужно тянуться к мыши, это ошибка;
- похожие действия делаются одинаково (место, вид, клавиша, тост с отменой);
- у настройки одна цель; разные цели — разные настройки;
- побочное действие не прячется (управление/просмотр/logoff — явные отдельные действия с подтверждением);
- выбор и курсор списка показаны только фоном выбора, без лишних полос/рамок;
- опасные действия (logoff, управление) — fail-closed, с номером заявки и подтверждением.
