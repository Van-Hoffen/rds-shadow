# Как выпускать релиз

1. Обновить `version` в `[workspace.package]` (`Cargo.toml`). Версия одно на весь workspace.
2. Прогнать локально:

   ```bash
   cargo fmt --all --check
   cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   ```

3. Закоммитить и запушить в `main`.
4. Поставить тег и запушить его:

   ```bash
   git tag v0.1.0
   git push origin v0.1.0
   ```

5. Workflow `Release` соберёт:
   - `rds-shadow-windows-x64.zip` — клиент и просмотрщик для Windows, пример INI;
   - `rds-shadow-audit-linux-x64.tar.gz` — просмотрщик для Linux.
6. Публикация упадёт, если тег не совпадает с версией workspace. Это защита от релиза «не той» сборки.
7. Черновик заметок GitHub формирует сам. Перед публикацией их можно отредактировать: события безопасности и изменения конфигурации писать явно.

## Что не делает CI

- Не подписывает бинарники. Для распространения внутри домена нужна подпись кода; это отдельная задача.
- Не проверяет теневое подключение: для него нужен Windows-стенд с Rds.
- Не публикует приватные имена узлов: их нет в репозитории.
